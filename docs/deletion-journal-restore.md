# Independent deletion journal and offline restore

The application writes a durable deletion intent before deleting any photograph or database row. New intents contain schema version 2, an HMAC-SHA256 owner token, HMAC-SHA256 image-key tokens, and a signature over the canonical record. It contains no raw account ID, email, name, image path, IP, clinical data, or request payload. These tokens remain pseudonymous personal data: restrict access accordingly. Use a separate random secret of at least 32 characters, never SECRET_KEY. Retain the key while any recoverable backup or intent exists. Key rotation requires an explicit dual-key migration; changing it directly makes old intents unverifiable.

Configure DELETION_JOURNAL_CONNECTION_STRING, DELETION_JOURNAL_CONTAINER, DELETION_JOURNAL_HMAC_KEY and DELETION_JOURNAL_REQUIRED=true. Test/development can leave the journal disabled; managed staging/production readiness now refuses to report ready without a configured private required journal. Metadata health does not prove write permission: a synthetic create/read/replay rehearsal is required before rollout.

Provision a dedicated private journal storage account outside the database/photo backup and restore boundary. Do not restore or roll it back with the application. No database migration is needed. The photo policy disallows retained historical images; the journal has a different purpose and must have independent protection against accidental deletion/rollback. The implementation currently uses a connection string; account-key access is broader than an ideal identity role. Before production enablement, restrict network access and secret access, use a dedicated account, and establish an independently protected journal backup. A restore cannot proceed when journal completeness is uncertain. Application credentials must not be shared with photo or production admin credentials.

Owner: Primary project owner (temporary), carrying release/recovery/privacy/on-call until explicit delegation. Gmail is an alert destination only; named delegation/contact details are required before broader operations. Current journal/key expiry is FAIL-CLOSED / DISABLED INDEFINITELY for unknown legacy sources. Future conditional target is 42 days after last modification, conditional on every DB/photo backup being retained for at most 35 days and recovery quarantine at most seven days. Current Azure DB retention is seven days. Untracked exports, legal preservation, or longer archive retention invalidate fixed 42-day expiration; retain corresponding intents and key until all recoverable copies expire. Do not enable lifecycle expiration until owners inventory every backup/export and restored/quarantined copy, including off-platform copies. Recovery must not create an untracked long-lived copy or silently reset allowed lifetime. Retain intents until the last recoverable copy is demonstrably gone; retain keys until all copies AND retained signed intents no longer need them. Age 42 days is a minimum eligible age, never permission to delete needed intents/keys. `validate_recovery_horizon` and `journal_expiration_eligible` in `app.core.operational_targets` provide tested offline review safeguards for 35+7 days, unknown inventory, legal holds and surviving copies; they delete nothing and install no lifecycle rule. The journal created in this rehearsal is synthetic and temporary, not a production retention implementation.

A failed DB commit or partial Blob delete leaves a durable pending privacy request. Retrying the same canonical owner/image set resolves to the same immutable object and is idempotent. Additional image sets create additional intents; replay unions all verified records. A recorded intent means the owner requested deletion; replay enforces it even if the original DB transaction failed. The accepted operational plan enforces recorded deletion requests even after an original transaction failure; the recovery/privacy owner must understand this when approving restore evidence. The live failed-deletion account remains until retry; this is not a queue worker or a guarantee of automatic online completion. Observe/retry failed privacy requests through restricted operational procedures without logging IDs.

**Phase 0: PASS for policy/design readiness under indefinite fail-closed retention.** This is not production rollout or production compliance certification. No concrete unresolved Phase 0 policy blocker remains: uncertain legacy and undiscovered external copies are conservatively covered by indefinite retention and reviewed manual recovery. A complete bounded inventory is required only for future expiry re-enablement. Production remains untouched; historical evidence below is preserved and has not been refreshed through production access in this task.

OneDrive copies are **LEGACY/UNKNOWN-PROVENANCE**, potentially production-derived recoverable sources. Their retention/history/holds and quarantine are unknown; no <=35-day horizon is certified. **Deletion-journal and HMAC key expiry is FAIL-CLOSED / DISABLED INDEFINITELY** while any unknown recoverable source exists or its retention/hold state is unknown. No age-based cleanup or lifecycle expiry may be enabled. The 42-day rule is a future conditional target only: every source must have proven provenance, lifetime <=35d, quarantine <=7d and no hold; no surviving recoverable copy may need the intent, and keys must outlive retained signed intents. Unknown off-platform/other-device copies are also covered by this indefinite block; this does not assert they are absent.

Legacy sources are excluded from automatic restore selection and are **not valid operational production restore sources**. Any exceptional use requires explicit recovery/privacy review by the Primary project owner (temporary), registration of every derived target, isolated offline recovery with traffic/writes disabled, complete independent journal coverage and verified signed deletion-tombstone replay before any traffic/writes resume. Unknown journal completeness, an unverifiable legacy identity/image mapping, or failed replay means recovery cannot proceed. Legacy copies do not meet the operational RPO and cannot be selected as an automatic fallback. Neither these files nor their cloud history were edited/deleted.

MVP owner: **Primary project owner (temporary)** carries release, recovery, privacy and on-call responsibilities until explicitly delegated. No real-world identity is inferred. The working Gmail receiver is an alert destination only. Named delegation and verified contact/escalation details are required before broader production/on-call operations.

See [durable legacy inventory](legacy-recoverable-sources.json) and [restore procedure](deletion-journal-restore.md). Accepted startup 180s, DB RPO <=5m and RTO <=30m remain unchanged. Protected production journal/key provisioning, independent protection/backup, completeness and replay verification (including legacy mapping), runtime/migrator least privilege, health endpoints/deployment, production alert routing and traffic-opening smoke remain **unimplemented/unverified production rollout steps**, not completed Phase 0 evidence. A failed rollout preflight must keep traffic closed.

Restore procedure (operational Azure PITR only; legacy sources require the exceptional review above):

1. Restore Azure PostgreSQL to a separate offline target. Keep public traffic and all writes disabled. Verify TLS with sslmode=verify-full and trusted CA, collation, version, baseline revision and constraints. Do not overwrite production.
2. Restore photographs to a separate private nonproduction target if needed. Never restore the journal with them. Inventory snapshots, versions and deleted objects; the existing photo deletion service refuses retained versions/soft-deleted copies until independently purged and verified.
3. Configure the restored target with its least-privilege runtime credential and the current independent journal and HMAC key. Validate that the journal is complete and protected, including all requests since the selected restore point. No journal mutation/deletion during validation.
4. Run `python -m app.tools.replay_deletions --offline-restore-target EXACT_RESTORED_POSTGRES_HOST` with ENVIRONMENT=test or staging and DELETION_JOURNAL_REQUIRED=true. Every signature is checked before mutation. Scan restored users against owner tokens, use the normal deletion service, then scan all restored Blob names against owner/image tokens to catch legacy and orphan uploads. Failed cleanup prevents successful completion. Repair the cause, retry and verify again.
5. Independently verify no matching users, associated rows, live images, snapshots, deleted blobs or versions remain. Repeat replay to prove idempotence. Record counts/timings only. Confirm application grants and smoke operations on the offline target.
6. Recovery owner approves evidence and accepted RPO/RTO before any separately authorized traffic switch. The command deliberately refuses ENVIRONMENT=production; traffic enablement remains a manual approved release step.

The HMAC scan needs full restored user and Blob inventory and therefore scales linearly. The current rehearsal uses a small synthetic population. Bound production inventory size and benchmark a complete replay before accepting RTO. Known legacy anonymous orphan images cannot be attributed after restore unless their names were recorded or their owner namespace remains; inventory/repair such historical objects before rollout.


## Accepted recovery objectives and validation (8 October 2026)

DB RPO <=5 minutes and end-to-end RTO <=30 minutes are accepted MVP targets. Same-region Azure PITR is the rehearsed recovery path; geo-restore is not certified against the five-minute RPO (Microsoft documents up to one hour for asynchronous geo-copy). Azure native backup retention is 7..35 days, and WAL archival delay generally reaches up to five minutes. This supports the chosen targets but does not prove a particular live restore point or bound recovery at larger scale. Always check actual restore availability and include network/grants/TLS/replay/smoke in the RTO; remain offline when objectives or journal completeness cannot be met.

The staging server was re-read on 8 October: PostgreSQL 18, Ready, seven-day backup, geo backup disabled. A 35-day horizon applies to *every* recoverable copy, not merely the managed server: independent exports, on-demand/long-term archives, restored server backups and legal preservation need their own inventory. Keep expiration disabled when any lifetime is unknown or exceeds the target. The seven-day quarantine is counted after the source copy's maximum 35-day lifetime; it is not renewed on every restore. A copy left accessible at day 42 blocks intent/key expiry even if the normal policy would have deleted it. Key retirement also requires all retained signed intents to be gone or re-signed through a reviewed dual-key migration.

Reference: [Azure PostgreSQL backup/restore behavior](https://learn.microsoft.com/en-us/azure/postgresql/backup-restore/concepts-backup-restore).


## Concurrency and durability contract (8 October 2026)

Schema 2 uses one **block blob per canonical intent**, named `v2/<SHA256(canonical record)>.json`. The canonical record has schema, HMAC owner token, and sorted unique HMAC image tokens. The envelope HMAC covers the complete canonical record. No writer reads/merges/replaces another intent. An owner may have many records, including an empty-image account deletion. Duplicate sets, reordered images and duplicate image references resolve to one object.

`upload_blob(blob_type="BlockBlob", overwrite=False)` is Azure atomic create-if-absent. Only `ResourceExistsError` is treated as a possible duplicate; the writer then downloads, verifies the signature and compares the exact intended record. Successful creates also require this read-back. There is no conflict merge loop, lease or shared mutable index. SDK network retries are bounded (two for configured clients); final errors propagate. A response lost after persistence is unacknowledged until an explicit deterministic retry verifies it. A crash before persistence leaves no acknowledgement; a crash afterward may leave a pending intent, which recovery must enforce. Storage unavailability, key failure, mismatched existing content and invalid signatures prevent destructive account work.

The count invariant is **unique acknowledged canonical intents == durable verifiable records** in a clean isolated test inventory. Successful duplicate calls count separately but share one durable intent. Unacknowledged ambiguous writes may produce additional pending records; do not interpret a larger inventory as a reason to discard them. Read-back proves persistence at acknowledgement time, not protection against subsequent privileged deletion/rollback. HMAC cannot detect removal of an entire valid record. Independently protected inventory/checkpoints and backups remain mandatory for completeness and future production protection.

The reader accepts schema 1 at its original `<owner-token>.json` path and schema 2 only at its content-derived path. Mixed inventories replay together; existing staging v1 records are not rewritten, deleted or automatically re-signed. This preserves surviving evidence but cannot reconstruct evidence already lost by a v1 race. Reconcile staging legacy evidence from an authorized independent source before claiming historical completeness. Freeze all old v1 writers before switching: mixed **readers** are supported, concurrent legacy overwrite writers are not safe. Reject unknown schemas, noncanonical v2 arrays, invalid signatures and path mismatches.

Replay verifies the entire source inventory before any mutation. The account callback receives the source journal in read-only mode and revalidates owner coverage and explicit legacy image tokens before account destruction. Namespaced orphan images are matched by owner; legacy anonymous images require an explicit image token. Replay never calls `record()` or replaces its source. All writers must be paused during a restore completeness snapshot; new intents arriving after the snapshot require another complete replay before traffic. Inventory scans are linear; per-account coverage rechecks add cost and must be benchmarked at rollout scale.

Rehearsal: run `python backend/app/tools/validate_journal_nonproduction.py` from the repository root with authenticated Azure CLI. This tool is pinned to the existing nonproduction resource group/account, checks its `production=false` tag, uses two fresh private containers and an in-memory synthetic database, keeps credentials/key in memory, emits counts only, and deletes only its created containers. It performs real Azure create conflicts, concurrent batches, signed replay through the real account deletion service, repeat replay, corruption and absent-container failure. It never reads staging journal contents or changes staging settings. Counts-only evidence is under `docs/evidence/journal-concurrency-20261008/`.

Before production Phase 2: separately authorize it; freeze legacy writers; provision the dedicated independent protected account/backup and separate key; keep expiry disabled indefinitely; verify private access, least privilege, rollback protection, complete enablement checkpoint and historical coverage exclusions; rehearse synthetic acknowledgement/replay on an isolated target. No deployment/Phase 3 is authorized by this nonproduction milestone.

Azure API contract: [BlobClient upload_blob](https://learn.microsoft.com/python/api/azure-storage-blob/azure.storage.blob.blobclient) documents `overwrite=False` conflicts for block blobs. Append blobs have different behavior; this implementation explicitly selects BlockBlob.
