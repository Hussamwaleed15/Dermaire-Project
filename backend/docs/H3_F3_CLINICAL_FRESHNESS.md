# H3-F3: current evaluation provenance and historical decisions

Audited registered /safety, /doctor/review-status, /doctor/patients/{patient_id}/reviews, review write, timeline, /home and /personal-skin-model; deterministic safety service, patient-visible filtering, frozen safety_snapshot and review sequence authority. No new clinical decision rules or database migration.

SafetyEvaluation adds nullable provenance for legacy typed snapshots. New dynamic evaluations always populate schema_version1, random evaluation_id per evaluation, source=deterministic_safety_engine, mode=dynamic_current, as_of equal to evaluated_at, source_revision SHA256 of fetched owner/source values, consistency=multiple_reads_not_atomic_snapshot, report_freshness=current|stale|missing, latest_report_at UTC|null, evidence_completeness=partial|screen_complete, clinical_clearance=false. Existing status/engine_version/reasons/evidence_status/guidance/limitations remain. screen_complete means existing latest structured screen has all fields and no unknown active-product IDs; it is never a claim of complete clinical evidence or clearance.

Fingerprint covers fetched check-ins, experiments/evaluations, product-intelligence projection, profile context, captures/measurements, daily contexts, active entries and adherence. It is an opaque input change detector, NOT monotonic revision, ETag/precondition, portable cross-database canonical identity, historical full snapshot storage, or an atomic transaction ID. Evaluation identity is not an operation receipt and has no lookup endpoint. Time passage may change interpretation even when the input fingerprint is unchanged. No patient data/credentials are exposed by the fingerprint; no token/password fields are included.

Report freshness uses the existing72-hour current window; older validated reports =>stale, none=>missing. Existing14-day triage rules and escalation precedence remain unchanged. Those are product rules, not validated medical clearance lifetimes. Missing evidence remains partial and existing guidance explicitly does not rule out risk. Source failures propagate unsuccessful HTTP500/503; no failed/unavailable source is converted to a successful reassuring result.

GET /home adds current full safety evaluation and consistency marker. Observation completion/measurement/baseline remain separate. GET /safety and nested doctor/PSM evaluations use the same engine, but separate requests have different identities/times and can observe source changes. Home as_of is its evaluation cutoff, not proof of one repeatable-read transaction across every source. Database READ COMMITTED and multiple selects can observe intervening commits. Cross-endpoint atomic snapshot/history cursor remains OPEN.

Doctor review outputs add is_current (sequence equality), resource_revision=immutable sequence, safety_at_review_kind=historical_saved, current_safety_evaluation_id, clinical_clearance=false. GET status adds as_of, consistency and current_decision_visibility=available|absent|not_available_to_patient. Latest private decision still yields current_decision:null; visible older history remains is_current:false. Existing state/latest_sequence/changed_at/changed_by semantics remain. No private rationale/notes/snapshot is promoted or disclosed. Saved safety_at_review retains its original payload and evaluation time/identity; the outer historical_saved label describes its use now, even when the originally saved provenance.mode was dynamic_current.

PSM doctor sources add matching current/history revision/visibility and consistency metadata. PSM Safety shares the canonical engine output; AI never overrides it. Historical follow-up remains free text/status, never a scheduled appointment. Clinician sequencing, owner/grant checks and revocation remain unchanged. Timeline review records identify latest sequence within that read; not a continuous change feed.

Compatibility is additive. Flutter must treat clinical_clearance=false literally, use as_of and freshness only with their documented scope, refresh after conflicts/account switching, and preserve unknown/error states. No client should compare an older positive cached result as current clearance. No Flutter edits.
