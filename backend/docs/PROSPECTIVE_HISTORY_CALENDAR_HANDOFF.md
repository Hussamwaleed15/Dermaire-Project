# Prospective routine evidence and account calendar contract

Migration `20261015_11` follows `20261015_10`. It adds empty tables and invents no historical evidence. Future ORM routine create/change/stop writes append immutable configuration snapshots in the source transaction, including experiment intervention and product archive writers. Linked product name/brand/status/ingredients/instructions changes append product evidence snapshots. CAS reservation-only flushes do not invent configuration events. Rolling back the source transaction also rolls back events and reminder cancellation. Raw maintenance SQL is outside this ORM capture contract and requires its own explicit evidence procedure.

`GET /api/v1/routine/configuration-history?routine_entry_id=<optional>&limit=100&cursor=<optional>` requires the owner bearer token. It returns `schema_version`, `day_basis: UTC`, `coverage: prospective_orm_writes_no_backfill`, `as_of`, `items` and `next_cursor`. Items contain immutable snapshots, event kind, created_at, routine_entry_id and schema_version. A snapshot records routine revision/configuration/source timestamps and contemporaneous product evidence; it does not reconstruct a clinically validated past regimen. Cursors are signed, expire after one hour, and bind account plus routine filter. Invalid/scope mismatched cursors return 422; expired cursors return 410; foreign entry filter returns 404. Responses disable caching. Ordering is created_at descending then ID descending. The timestamp cutoff is explicitly **not an atomic database snapshot**: a previously in-flight transaction may commit later. Restart history for fresh evidence; never use these pages as an atomic clinical evidence export.

`GET /api/v1/routine/calendar-policy` returns the current policy, initially revision 0 and UTC. `PUT` accepts only `{ "timezone": "Africa/Cairo", "expected_revision": 0 }`. An unsupported IANA zone or extra fields return 422. The update takes the same owner lock used by routine writes and appends an immutable revision effective at the server commit transaction's recorded instant. Concurrent stale expected revision returns 412. Retrying the current identical zone/revision is a no-op; after an unknown 503 outcome, GET the current policy before deciding whether to retry. No client backdating is accepted. GET provides local_today derived from an absolute instant, which makes DST gaps/folds unambiguous. Travel can move the displayed local day backwards or forwards; it never rewrites prior evidence or creates an additional adherence slot.

Legacy routine start/end dates, adherence date validation and `(entry,date,slot)` uniqueness remain UTC. There is **no local-day adherence migration** in this increment. The account timezone labels are prospective display context; recurring reminders use their separately approved explicit timezone/fold/gap settings. UI must label adherence days UTC and must not submit a local calendar label as though the backend had migrated those keys. A future local-day adherence namespace needs a separately versioned contract and explicit migration policy; no old dates may be silently reinterpreted.

All routine revision/configuration changes transactionally cancel pending routine notices and jobs and clear leases. Already provider-accepted attempts retain their historical state because cancellation cannot unsend a provider acceptance. Account deletion purges configuration snapshots, calendar policy revisions, and routine reminder settings before deleting linked routine rows. No PHI is added to push payloads by these hooks.

Focused verification includes SQLite API lifecycle/history/cursor/privacy/immutability/rollback, UTC-label midnight and DST gap/fold/travel cases, and real isolated PostgreSQL configuration CAS winner/loser rollback (3 cases), calendar concurrent CAS (1 case), and reminder cancellation commit/rollback (2 cases). These tests provide no model or clinical validation and no live delivery proof.

Provenance refinement: authenticated routine writers now record actor_id and exact routine create/update/stop operation. Product-driven events identify the product update/deactivation source and product ID/status. Experiment interventions identify the committed experiment ID and intervention type. Attribution is bound to the current source transaction; untagged internal ORM writes explicitly record null actor_id and unattributed_orm_write rather than inventing an actor from ownership. owner_id remains separately identified. History pages expose coverage_since and last_evidence_at for the selected account/filter and cutoff; both are null when no captured events exist. These indicate first/last observed future evidence, not completeness before that date or current clinical-state verification. freshness is explicitly event_history_not_current_state_verification.

Privacy erasure refinement: each event has an immutable indexed source_product_id. Its routine foreign key uses ON DELETE CASCADE: public routine deletion still stops entries, while explicit internal source hard deletion erases dependent evidence rather than blocking established restore/cleanup operations. Account purge remains an explicit dependency-ordered bulk delete. Normal product erasure and signed product replay bulk-delete only events matching exact typed owner/product references; no immutable snapshot is edited. Replay verifies signed intents and restored dependencies before mutation and also clears matching historical evidence when the product row is absent. Other owners and other product evidence are preserved. These narrowly scoped privacy erasures are exceptions to append-only retention.
